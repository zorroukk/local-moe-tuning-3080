# MoE decode-speed levers — consumer NVIDIA + RAM-resident experts

Decision table for raising tg (decode) on a rig where the model exceeds VRAM and experts stream from system RAM (e.g. 3080 10GB + 32GB, 35B-A3B Q4_K_M, ngl 99 ncmoe 30). tg is RAM-bandwidth-bound: levers either read fewer bytes per token or read them faster. Baseline on this rig: tg ~43 t/s on Q4_K_M; 52.5 after the 2026-10-28 APEX-MTP-I-Compact swap; **~59–60 t/s since the same day's external MTP-Q8_0 draft head + mlock (current production baseline)**.

## Prefill levers for experts-on-CPU rigs (davetha/llama-moe-hybrid-tuning, cross-vendor, same arch)

- **`--no-mmap` ≈ 2.4× prefill** when experts sit in CPU RAM (mmap'd experts page-fault every token; llama.cpp prints "consider using --no-mmap" with CPU experts). Free on big-RAM hosts.
- **`-ub 2048 -b 2048` ≈ another 2.7× prefill** (default -ub 512). Grows GPU compute buffer — validate with a real large prefill, keep ~1 GB VRAM headroom; overcommit can wedge the GPU, not clean-OOM.
- Generation barely moves (bandwidth-bound) — these are PROMPT-side wins, which is what agent traffic suffers at.
- **Context checkpoints on GDN hybrids**: upstream checkpoint bugs for hybrid/recurrent models (restore never fires; end-of-prompt-only checkpointing invalidating follow-ups) are build-specific — **measured WORKING on this rig's b11935**: follow-up turns process ~0 new tokens, shared prefixes reuse at ~8× cold pp. Never adopt a fork for a checkpoint fix before probing locally with `scripts/ckpt-reuse-probe.py` (2-turn chat; turn-2 `new_tokens_processed` ~0 = works, ≈ full in = bug). The gateway strips `prompt_eval_count` from `timings` — probe llama-server directly, or derive new tokens as `(wall − out/tg) × pp`. GDN recurrent state cannot drop middle spans — any prefix edit re-prefills from divergence; keep compaction stable-prefix.
- **Reasoning preservation (`preserve_thinking`) is ON by default** on b11935 with `--jinja` for this model family — the server logs it at startup (`--no-reasoning-preserve` disables). Don't wire extra `chat_template_kwargs` hoping to enable it; check the launch log first.
- **`--no-mmap` current spelling is `--load-mode none`** — the loader itself warns `tensor overrides to CPU are used with mmap enabled - consider using --load-mode none`; that warning line is the confirmation the prefill lever applies to a launch.
- **RAM math for `--load-mode none` on a 32 GB host**: plain no-mmap with f16 KV at 64k = server NEVER_READY (18 GB private model + ~5 GB KV overshoots). Halve KV first (`-ctk q8_0 -ctv q8_0`) or drop ctx for that round only.
- **Round I verdict (2026-10-28): the prefill lever is DEAD on b11935.** The combo that fits (Compact 17.4 GB + q8_0 KV) LOADS but pp 45.2 vs mlock 47.0 — davetha's 2.4× does NOT reproduce on current builds (their notes predate the b11935 era); `+ -b 2048 -ub 2048` measured worse (42.2). Also rejected: auto-offload (Qwen forum #37 recipe: drop ngl/ncmoe, let `--fit` auto) — best pp of the round (48.6) but tg −3% and re-opens the VRAM-estimator cliff. Every flag lever now measured neutral-or-negative on this rig; production flags are final.
- **`--load-mode mlock` = the anti-thrash reliability lever — MEASURED, LIVE IN PRODUCTION since 2026-10-28** (b11935 help.txt: force model to stay in RAM, no pageout). Directly targets the documented Windows failure mode where the OS trims the server working set (observed 12/21.9 GB trimmed → decode 4–8 t/s). Round H on the Compact: tg 52.5 / pp 45.5 vs base 49.8 / 39.3 (steady reps 53.7 = best of round) — neutral-to-positive on speed, free insurance. Proof of activation: zero `failed to mlock` lines AND the `mmap enabled - consider --load-mode none` warning disappears. Costs pinned RAM.
- **Draft-head quality is a variable, not fixed** — the built-in MTP head in a quant file is often low precision (APEX ladder head = Q3_K ~0.4 GB; the 27% acceptance measured here is that head's ceiling, not the arch's). Publishers sometimes ship a standalone higher-precision draft head (e.g. `mtp-<model>-Q8_0.gguf`, ~2 GB) that attaches to any quant of the same base model: `--model-draft <head> -ngld 99 --spec-type draft-mtp --spec-draft-n-max N`; a Q8_0 head is reported at ~2× the acceptance of built-in low-bit heads on code traffic. The draft head costs VRAM — free room with q8_0 KV. Before rejecting MTP for a model, check the publisher repo for a standalone head. **MEASURED 2026-10-28 (Round J/K, LIVE):** AtomicChat `mtp-Ornith-1.5-35B-A3B-Q8_0.gguf` on the Compact → 81.6% accept at n-max 1, tg +10%, reuse probe passed; the 2 GB head fit in VRAM alongside 64k f16 KV with no q8_0 KV needed. n-max 1 is the winner on this rig (matches the publisher's own sweep: their n1 83.3%/1.22×, ours 81.6%/1.11×).
- Spec-decode verdicts are RIG-DEPENDENT (same arch: −19% on B580, +22% on another box, −33% untuned here) — always local-sweep n-max {1,3} × p-min before believing any MTP claim. On hybrids, speculation can ALSO silently destroy prompt-cache reuse (accepted draft tokens past end-of-turn stop the slot being a prefix of the next request) — judge any spec-decode round on tg AND turn-2 reuse, never tg alone; a −30% tg reading may be cache damage, not the drafter. That EOG bug is llama.cpp #28049, **fixed upstream Sep 29 2026 (PR #29638)** — builds after that date should pass the reuse probe with MTP on; older builds' MTP losses may be cache damage. ik_llama.cpp's MTP acceptance bug #1814 was fixed May 2026 (#1815/#1816); its fused delta-net kernels are real (3090: 142–146 t/s on this class) but its checkpoint story is messy (fix PR #1976 vs earlier revert) — keep it a phase-2 second runtime.

## Check whether a GGUF carries an MTP head before planning draft-mtp

Offloader formula from peculiar-ragdoll (validated on this rig): `n-cpu-moe = 40 − floor((VRAM_GB − 4.3)/0.49)` → 10 GB → 30 = the live setting. Never pass ncmoe 41 on a 40-block MTP ladder (block 40 IS the draft head — 41 puts the drafter on CPU). Never lower `-ngl` to fit; push routed experts to CPU only. draft-mtp known-broken on Turing sm_75 (llama.cpp #24670); confirm activation via `statistics draft-mtp` lines in stderr.

Fast bytescan of the header region (tensor names and KV keys live in the first few MB; a hand-rolled GGUF KV parser is easy to desync — prefer the scan):

```python
import re
head = open(MODEL_GGUF, "rb").read(8_000_000)
print(re.findall(rb"[a-zA-Z0-9._]{0,40}mtp[a-zA-Z0-9._]{0,40}", head, re.I))
```

Filter false positives from the embedded vocab ("SMTP" etc.). No `blk.N.mtp.*`-style tensor names → `draft-mtp` is unavailable for that file; ngram speculation still works (needs no head). MTP-carrying conversions of Ornith-1.5-35B-A3B: mudler APEX-MTP ladder (Compact 17.44 GB / Quality 23.72 GB, I-variants imatrix; head = fixed Q3_K ~0.4 GB) and peculiar-ragdoll Tiel-Coder-MTP (UD ladder, abliterated + Sharp template — behavior change, not just speed). A hand-rolled GGUF v3 KV parser desyncs easily (array encoding); the server loader is the real judge — `common_speculative_init_result: creating MTP draft context` in stderr confirms the head.

## Predict tg for a candidate quant BEFORE downloading

On a bandwidth-bound rig, decode scales inversely with file size: **tg ≈ 910 / file_GB, ±5% for same-quant-shape swaps** (validated twice on the 3080 rig: predicted 41.8 vs measured 43.8 for Q4_K_M; predicted +25% vs measured +20% for the Compact swap). **Quant SHAPE matters, not just bytes**: Tiel IQ4_XS 18.12 GB measured tg 40.1 — the rule predicted 50, Compact (17.44 GB, mixed imatrix ladder) measured 52.5. IQ4_XS decodes ~20% worse per byte than a mixed Q4-ladder of equal size (narrow CUDA kernels); the IQ3 tier is worse still — AD-IQ3_S-IQ3_XXS 15.51 GB (−11% bytes vs Compact) measured tg 43.9 vs 52.5 (−17%) while the rule predicted 58.7: the shape penalty compounds as bits shrink, so smaller-quant speed plays are DEAD on this rig until a runtime with better narrow kernels (ik_llama.cpp). When ranking candidates, apply the rule only within the same quant family; across families treat the prediction as ±25%. Download big files with `scripts/hf-parallel-dl.sh` (HF throttles single connections to ~1 MB/s; 16 range-connections hit ~10 MB/s) — pin `TOTAL` to the exact byte size from `https://huggingface.co/api/models/<repo>/tree/main`.

**Quality gate before a quant-drop win is promoted**: prefer ladders whose publisher publishes KL-divergence + Top-1 agreement against the BF16 reference (AtomicChat's AD ladder for Ornith-1.5-35B-A3B publishes the full table; `AD` per-tensor layouts beat stock presets at equal size — e.g. AD-Q4_K-IQ4_XS beats stock Q4_K_M at 1 GB smaller and 34% lower divergence). Top-1 agreement below ~90% (the IQ3 tier here: 88.1% at KLD 0.087 vs ~0.03 at the Q4 tier) is a quality cliff for agent/tool-call traffic — a speed win at that rung must pass the quality A/B harness before promotion, per the DR-insurance selection axis.

## Bench method for any candidate flag

llama-bench rejects llama-server-only flags — cycle real `llama-server` launches with production flags + candidate, probe with `scripts/decode-probe.py` (reads the response `timings` object), supervisor task DISABLED for the whole round, and gate the round on the baseline config reproducing the known live number. Re-run the baseline as the LAST cycle too: the first cycle after killing the old server starts with the old model's page cache unreclaimed (free-RAM reads low) and reads depressed — a first-cycle regression is suspect until the clean re-run agrees. For rounds touching speculation or cache flags, interleave `scripts/ckpt-reuse-probe.py` once per judged config. Probe gotcha (b11935): `/health` answers `ok` while the model is still loading — chat returns 503 until weights are up; probes must retry the chat request itself, not trust `/health`. A 502 from the gateway right after a bench cycle = scheduled task reloading the model, self-heals ~2 min..
